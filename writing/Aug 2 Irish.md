Seachtain → seachtain+Noun+Fem+Com+Sg


roimh → roimh+Prep+Simp


Shamhain → Samhain+Noun+Fem+Com+Sg+Len


chuaigh → téigh+Verb+VTI+PastInd+Len


an Seónstanach → definite NP, subject


siar → directional adverb


seacht → crucially seacht+Num+Card+Ecl


ngearráin → gearrán+Noun+Masc+Com+Pl+Ecl, not the genitive-singular analysis


péire → péire+Noun+Masc+Com+Sg


cliabh → genitive plural after péire: cliabh+Noun+…+Gen+Weak+Pl


ar gach gearrán → straightforward PP, “on each pony”


faoi choinne → correctly recognised as a compound preposition, essentially “for / in order to get”


a chuid → a = 3sg masculine possessive + cuid, “his share/quantity [of …]”


and then the omitted final ime, “of butter”, should be the genitive of im.


The particularly nice bit is seacht ngearráin. The analyser actually contains exactly the information we want:
seacht+Num+Card+Ecl
gearrán+Noun+Masc+Com+Pl+Ecl
So it recognises the historically/orthographically interesting eclipsis after the numeral and does not force ngearráin to be singular simply because the form is compatible with genitive singular.
There are a few syntactic oddities.
Seachtain as @NP is locally reasonable but misses the role of the whole constituent:

Seachtain roimh Shamhain
“a week before Samhain”

is a temporal adverbial modifying chuaigh. So in UD-ish terms I'd want the NP headed by Seachtain attached to chuaigh as obl:tmod (or obl, depending on the annotation scheme), with roimh Shamhain modifying Seachtain.
Likewise the parser calling seacht ngearráin an @OBJ is suspicious because téigh doesn't take it as a normal direct object. The construction is effectively:

chuaigh an Seónstanach siar agus seacht ngearráin ...
the Johnston man went west with seven ponies ...

That old Irish pattern of agus NP accompanying a motion/event participant is precisely the sort of thing a tag-based dependency parser is liable to mistake for ordinary coordination/objecthood. Semantically, the ponies accompany the man; they aren't something he “went” transitively.
And this:

faoi → lemma faoi_choinne, Prep+Cmpd

is revealing about the tokenizer. It has apparently consumed choinne as part of a multiword lexical item while emitting only faoi as the surface token in this report. So its absence from the HTML isn't necessarily a failure to analyse it.
The ending should decompose as:
faoi choinne a chuid ime
for.to his share butter.GEN
approximately:

“for his butter” / “to fetch his supply of butter”

with ime depending on cuid, rather than cuid being the endpoint of the PP as this truncated output makes it appear.
So, modulo the old dependency labels, the morphological output gives us a surprisingly good basis for a Leipzig gloss. The two selections that matter most are seacht+Num+Card+Ecl and ngearráin+…+Com+Pl+Ecl.

Exactly. For lemma and POS, I wouldn't really treat the two outputs symmetrically at all. The old pipeline has a substantially stronger claim to authority.
In particular, there are two different things going on:


lexc constrains what analyses actually exist for a lexical item;


CG chooses among those analyses in context.


Whereas Stanza is predicting both from statistical regularities. So for something like
chuaigh  → téigh + VerbShamhain → Samhain + Noun
the dictionary analysis is qualitatively better evidence than Stanza happening to predict the same thing.
I'd therefore be tempted to construct the eventual annotation roughly as:
FORM        old pipeline                  Stanza            ↓                             ↓LEMMA   ← lexc + CGUPOS    ← mapped lexc/CG POSFEATS   ← lexc + CG where representable            ↓          CONLLU            ↑HEAD    ←──────────── StanzaDEPREL  ←──────────── Stanza
with some qualifications.
The obvious one is guessed analyses. Your example already gives:
Seónstanach+Guess+Prop+Noun+Masc+Com+Sg+@SUBJ
So that's conveniently distinguishable from a lexical analysis. I wouldn't let a Guess analysis automatically overrule Stanza in the same way that a dictionary entry would. You can retain something like Analysed=Lexicon versus Analysed=Guess in the intermediate representation.
Similarly, there'll presumably be cases where the lexicon itself is simply wrong, outdated, or has an analysis that you now know shouldn't be selected. But those are enumerable lexical defects, which is a much nicer problem than opaque tagging errors from a neural model. You can patch them.
And I think FEATS could benefit enormously too. Stanza might be perfectly good at common number/case combinations, but the morphological analyser knows things such as:
seacht+Num+Card+Eclngearráin+Noun+Masc+Com+Pl+Ecl
The UD conversion necessarily loses or reshapes some of that information. For your own stand-off representation there's no reason you need to lose it. You can map the ordinary material into UD:
UPOS=NOUNGender=MascNumber=PlurCase=Nom
while retaining, say,
Mutation=Ecl
in MISC or your own annotation layer.
In fact, I think that changes the purpose of running Stanza quite significantly. Rather than:

run Stanza, then use the old pipeline to check whether Stanza got the analysis right

I'd make it:

use the morphological pipeline to supply lexical annotation; use Stanza primarily to supply the parts you actually need it to infer.

Then disagreement becomes useful for quality control. If Stanza says VERB where the disambiguated lexical analysis says NOUN, flag it—but there's little reason to accept Stanza's POS merely because Stanza is the component producing the CoNLL-U.
That also avoids an odd circularity: since Stanza's Irish POS/lemma model ultimately learned from data descended from this analyzer anyway, you're replacing an imperfect learned approximation of the original information with the original information wherever it's still available.
The dependency parse is where the comparison becomes genuinely interesting rather than an obvious preference for one source. There I'd keep both for a while rather than immediately deciding that either the CG parser or Stanza is authoritative.

## Assistant

Yes — that is the key asymmetry.
The old pipeline is not giving you a single gold analysis; it is giving you a linguistically licensed candidate set after lexical analysis and partial CG disambiguation. So if Stanza lands inside that set, the result is at least compatible with the rule-based analysis. If it lands outside the set entirely, that is a much stronger signal.
I’d distinguish three cases:


Stanza matches the sole surviving analysis → high confidence.


Stanza matches one of several surviving analyses → compatible, but the old system remains ambiguous.


Stanza matches none of the surviving analyses → strong Stanza-error flag, subject mainly to tokenisation, lexicon gaps/errors, and feature-mapping mistakes.


That makes the old system particularly useful for lemma/POS/morphology validation without pretending it is exhaustive or gold.
The interesting quantity is therefore not simple agreement rate, but something like candidate-set coverage:
Stanza analysis∈{CG-surviving analyses}
For the non-membership cases, I’d probably inspect them first. They should be a very high-yield error sample, because Stanza has produced an analysis that neither the lexicon nor the contextual CG rules can support.
You could even preserve the candidate set in the stand-off data. That would let you distinguish “Stanza chose the wrong answer” from “the linguistic pipeline itself could not decide”, which is much more informative than reducing both to a single POS tag.
